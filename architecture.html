How ManeMap and Milo are actually built.

A live mobile product connects the interface, user data, retrieval and model behavior. Here is how I bring those parts together in ManeMap, the decisions behind the implementation, and the evidence available to inspect.

System boundaries

One product, distinct responsibilities.

The engineering problem is to turn a question about a specific horse into a useful response with the right context, while keeping model behavior separate from application and data controls.

Interface

Shared mobile application.

Kotlin and Compose Multiplatform provide the current iOS and Android client. The app collects the question and active horse context, presents the response, and connects the conversation to care, training and daily workflows.

Application and data

Supabase orchestration.

PostgreSQL stores application data, with authentication and row-level access rules. Deno/TypeScript Edge Functions assemble context, call retrieval and model services, apply output checks and return the result.

Model boundary

Selected context in, text out.

Gemini receives the assembled prompt and selected context. Prompt instructions guide generation; application code handles retrieval, response processing and delivery. A model instruction does not replace a database permission or an output check.

Request path

From question to guarded answer.

Known emergency signals can route to a predefined response before normal generation. The stages below describe the retrieval and generation path; optional context and upstream failures also affect what is available to it.

  1. 01 · CLASSIFY

    Assess the risk first.

    Deterministic patterns route known emergency wording. A separate model classifier assesses symptom descriptions and paraphrases. These are complementary checks with different failure modes.

  2. 02 · RETRIEVE

    Find relevant evidence.

    The query embedding is checked for the configured 768 dimensions. A vector-search RPC requests five matches from the bilingual knowledge base using the question vector and language.

  3. 03 · ASSEMBLE

    Add the horse context.

    Retrieved passages are combined with the active horse profile, medical and care data, recent training and current weather when available.

  4. 04 · GENERATE

    Answer inside constraints.

    Gemini receives the assembled context and response rules, including the ban on diagnosis, medication instructions and invented personal data.

  5. 05 · SANITISE

    Check the output.

    Server-side sanitisation targets internal labels and unsafe medication detail, with veterinary redirection when needed. Pattern-based cleaning reduces specific risks; it cannot validate every medical statement.

Architecture decisions

Why this stack fits the product.

Each choice reduces operational complexity or gives me tighter control over a user-facing risk.

Client

Kotlin / Compose Multiplatform

I built the current shared Kotlin codebase after managing the first React Native version with an external team. This gives me direct ownership of implementation and releases across both stores. Platform integration and store QA still need separate attention.

Data and retrieval

Supabase + pgvector

Relational data, authentication, access rules, Edge Functions and vector retrieval stay in one backend stack. That reduces service coordination for a small product, while concentrating operational responsibilities in one platform.

Model layer

Gemini with explicit controls

The model handles generation and classification. Deterministic routing, selected context and output processing make specific requirements executable around it. Provider changes and probabilistic responses still require evaluation.

Retrieval and resilience

The useful detail is in the failure paths.

These implementation notes describe reviewed source. They are not a benchmark or a claim that every deployed answer follows an identical path.

Context assembly

Relevant to this horse.

Retrieved passages are combined with profile, medical, feeding, care and training information. Context fetches run in parallel where possible; weather is included when available. Keeping these inputs explicit makes missing or irrelevant context easier to diagnose.

Degraded retrieval

Grounding has conditions.

The reviewed source can proceed without retrieved passages if embeddings are unavailable. That distinguishes a context-based answer from one supported by retrieved knowledge. The public routing tests do not measure retrieval relevance or answer faithfulness.

Provider failures

Bounded work and timing.

The model integration includes timeout and cancellation handling, bounded retry attempts and different handling of failure classes. Stage-level timings cover embedding, retrieval and model work. These are diagnostic controls, not a published latency or availability guarantee.

Safety design

Controls at three points.

Health guidance can fail through missed urgency, unsafe wording or leaked internal detail. The pipeline addresses each failure at a different stage.

Before generation

Emergency detection

Rules target known signals; the second classifier assesses paraphrases and symptom descriptions. Distinguishing educational questions from active incidents is an explicit routing requirement and a source of regression cases.

→
During generation

Response constraints

The prompt sets the response mode and instructs the model to avoid definitive diagnoses, prescribed medication detail and unrelated financial context in health situations. These instructions are constraints to test, not guarantees.

→
After generation

Output sanitisation

Server-side cleaning targets internal mode labels and named medication content before delivery. The product directs users to veterinary care; the assistant does not replace a veterinarian.

Verification

A test record with a defined scope.

Historical release evidence: Milo v117, deployed 21 August 2026. The published QA record compares deterministic emergency routing with v116 and documents both improvements and a remaining failure.

Offline routing

103 defined scenarios.

Zero unintended regressions; 27 newly routed cases; five intended false-positive reductions. One pre-existing German inflection case remained failing and documented. This is not a 103/103 pass claim.

Deployed smoke checks

12/12 probes passed.

The recorded probes checked gate state, selected category and medication-name leakage across specified language and routing scenarios. They are a small release sample, not exhaustive coverage of generated answers.

Test-driven change

Fix the decision, then recheck.

Tests exposed Spanish routing gaps, substring false positives and a category-ordering problem. The release added language coverage, used boundary matching and changed routing precedence. The record explains what changed and what remained open.

Evidence boundary

Specific results, honest limits.

The v117 record is a self-published release summary. It tests deterministic emergency routing, not clinical correctness, general retrieval quality, every generated answer or every subsequent release. Raw Milo runs and source code are private.

The public AskCV code and its dated regression record provide a separate, inspectable example of how I work with model boundaries and failure cases. Its results must not be transferred to Milo.
